# 杏林汇 · 架构模块化方案(DDD 域划分与迁移路径)

> P1 地基交付物之一。目标:在不中断线上服务的前提下,把当前"平铺式 FastAPI+单体 SPA"演进为边界清晰的领域化架构,为 P2-P4(多辨证体系/开放平台/国际化)铺路。

## 一、当前状态(基线)
- 后端:单 FastAPI 应用,`app/api/v1/*` 26 个路由文件、`app/models/*` 10+ 模型文件、`app/services/*` 十余服务,新老代码混排(痔漏/疮疡/总库/辨证/学苑/门诊)。
- 前端:单 Vite SPA,`src/views/*` + `src/modules/{surgery,pediatrics,alchemy}`。
- 已具备的工程化基础:P1-1 AI 网关(统一出网)、可观测性中间件、设备级身份。

## 二、目标架构:五个领域 + 专科插件层

```
app/
├── core/                  # 横切:配置/数据库/安全/网关/可观测性/设备身份
├── domains/
│   ├── knowledge/         # 知识总库(kb_*):目录/检索/关联/语义检索
│   ├── diagnosis/         # 辨证引擎:规则匹配/置信度/多体系(八纲/六经…)/AI 协商
│   ├── clinic/            # 门诊:就诊/处方/随访/PDF/导出
│   ├── learning/          # 学苑:路径/自测/笔记/助教
│   └── platform/          # 平台:访问统计/设备/版本
├── specialties/           # 专科插件层(数据+引擎+问诊模板,可插拔)
│   ├── surgery/  anorectal/  pediatrics/  alchemy/
└── api/v1/                # 薄路由层,仅编排 domain 服务
```

### 领域与聚合根
| 领域 | 聚合根 | 关键实体/值对象 |
|---|---|---|
| knowledge | 条目(方剂/中药/病种/证型/医案/术语/引药) | 出处、别名、组成、互链 |
| diagnosis | 辨证记录 | 四诊输入、候选证型(置信度)、证据链、AI 报告 |
| clinic | 就诊 | 患者、处方、随访 |
| learning | 学习进度 | 路径、自测卷、笔记、收藏 |
| platform | 设备 | 访问记录、统计窗口 |

### 依赖规则
`api → domain services → models`;领域间只通过**领域事件/接口**通信(如辨证完成后发 `DiagnosisCompleted` 供门诊/学苑订阅);`core` 不依赖任何领域。

### 专科插件契约(每个专科 = 一组可插拔资产)
1. `data`(kb module=xxx 数据 + 专科规则 JSON,如儿科 pediatrics-dx.json)
2. `engine`(辨证引擎函数:四诊→证型候选)
3. `intake`(问诊模板:四诊分类选择器分组,已实现为 fourDiagnosis.js 数据)
4. `knowledge`(知识条目、分期治法规则)
→ 新专科 = 添加一组资产 + 注册,无需改核心代码。

## 三、迁移路径(物理重构分三步,每步可独立上线)
1. **Step 1 建骨架(不搬代码)**:创建 `app/domains/*` 与 `app/specialties/*` 包,新代码一律进域包;旧代码保持原路径,`__init__` 提供兼容 re-export。
2. **Step 2 逐域搬迁(每域一次 PR)**:按 knowledge → diagnosis → clinic → learning → platform 顺序,把 models/services/routers 物理搬入,同时补域级单元测试;搬完一个域即发版验证(灰产兼容别名)。
3. **Step 3 契约化**:专科插件契约落地,把 surgery/anorectal/pediatrics/alchemy 的四诊模板与引擎注册进插件层;开放"新专科接入清单"文档。

## 四、验收标准
- 每个域:独立目录 + 域内依赖单向 + 单元测试 ≥80% 覆盖(核心逻辑);
- 搬迁期间:线上回归全绿(现有 15 页面 + 8 API 冒烟集);
- 新专科接入演练:以"内科(感冒/咳嗽)"为例,仅新增资产不碰核心代码完成接入(作为插件契约验证)。
