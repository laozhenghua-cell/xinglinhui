# 杏林汇 · 硬件接入详细方案(舌诊 / 脉诊 / 四诊仪)

> 版本 v1 · 2026-08-31
> 目的:回答"有什么硬件适合接入系统",把零成本(手机摄像头/麦克风)、消费级(PPG 手环/脉诊仪 SDK)、医院级(四诊仪网关)三档接入方案的技术细节全部展开,作为选型与实施依据。
> 原则:①硬件只做"客观采集",不做"替代医生诊断";②采集结果统一转成**症状/体征标签**喂给现有六体系辨证引擎(`analyze_systems`),不动辨证核心;③全开放免登录的设备级匿名(设备身份 = X-Real-IP + UA 加盐哈希)与写限流(30 次/分/IP)继续适用;④任何一档都要有评测集与回归,准确率可公开。

---

## 一、现状盘点(可挂接点)

| 已有能力 | 位置 | 硬件方案如何复用 |
|---|---|---|
| 多模态视觉网关 `vision(image_b64, prompt, provider="qwen")`(qwen-vl-max) | `app/core/ai_gateway.py:168` | A 档舌象照片 → 结构化舌象 JSON,零新增 AI 依赖 |
| 摄像头采集组件(已含 getUserMedia、拍照、上传) | `platform/web/src/components/ImageUploader.vue`、`views/diagnosis/ImageDiagnosis.vue:270` | A 档直接复用,加"拍摄引导+校准"即可 |
| 白话主诉解析(口语词库 346 条,DB 热更新) | `app/services/dx_systems.py` + `kb_synonyms` | A 档语音转文字后无缝接现有解析 |
| 六体系辨证引擎(舌象/脉象标签已参与打分) | `app/services/dx_systems.py:analyze_systems` | 所有档位的终点:标签并 `user_labels` |
| 脉证相参鉴别(真寒假热/真热假寒,靠"脉微细/脉沉数"等词触发) | `_discern()` | B 档脉诊仪自动产出脉象标签后**自动触发**鉴别 |
| 时间辨证(时辰规则)与五运六气(干支引擎) | `_time_dx()` / `_wuyun()` | B 档手环睡眠/昼夜节律数据可把"夜间加重"从口述变实测 |
| 设备级匿名记录(`dx_records`)、写限流、审计 | `app/api/v1/dx.py` | 新 device 模块沿用同一套身份与限流 |

**结论**:杏林汇缺的不是架构改造,而是"客观采集层"。三档方案共用同一个终点(标签 → 引擎),差异只在采集设备与数据通道。

## 二、总体架构(三层采集 + 一个 device 模块)

```
┌─────────────────────────── 采集层(硬件) ───────────────────────────┐
│  A 直连层        B SDK/导出层            C 网关层                    │
│  手机摄像头/麦克风  脉诊仪(Web蓝牙SDK)     医院级四诊仪(串口/网口/DB)   │
│       │  PPG手环(健康云导出)                  │                     │
└───────┼──────────────────┼────────────────────┼─────────────────────┘
        │ WebRTC/WebSpeech │ Web Bluetooth/HTTPS│ 设备网关(小主机,院内网)
        ▼                  ▼                    ▼
┌─────────────────────────── 平台层(杏林汇) ──────────────────────────┐
│  前端:拍摄引导/校准卡识别 · 蓝牙连接状态机 · 健康数据导入            │
│  后端:POST /api/v1/dx/analyze (symptoms + detail 扩展)              │
│  新增 device 模块:/device/readings 录入、设备注册表、特征提取服务     │
│  特征提取:舌象JSON/脉图参数 → 标签规则库 → user_labels               │
│       ▼                                                            │
│  analyze_systems(user_labels, time_key, sick_year, birth_year)     │
│  → 六体系 + 病机提要 + 脉证相参鉴别 + 时间辨证 + 五运六气 + 拟方      │
└────────────────────────────────────────────────────────────────────┘
```

新增 `device` 模块数据模型(PostgreSQL,`Base.metadata.create_all` 自动建表):

```sql
-- 设备读数(原始信号存 JSONB,特征提取后的标签另存,便于回溯与评测)
CREATE TABLE dx_device_readings (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    device_id TEXT NOT NULL,          -- 设备/采集源标识(加盐哈希,不存 PII)
    kind TEXT NOT NULL,               -- tongue_image | pulse_wave | ppg_export | simo_four
    raw JSONB NOT NULL DEFAULT '{}',  -- 原始数据(图片URL/波形数组/四诊仪JSON)
    labels JSONB NOT NULL DEFAULT '[]', -- 提取后的症状标签(喂给引擎的)
    meta JSONB NOT NULL DEFAULT '{}', -- 光照/校准/型号/固件版本
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_device_readings_kind_created ON dx_device_readings (kind, created_at DESC);
```

安全:读数走现有 `limit_ai` 写限流;设备身份沿用 `X-Real-IP+UA` 加盐哈希;舌象照片仅存设备级匿名对象存储,提供"删除本设备全部记录"入口(与现有记录删除一致)。

## 三、方案 A:手机摄像头舌诊拍照 + 语音问诊(零成本)

**目标**:不买任何设备,把"望(舌)、闻(声)"客观化,落地遗留项"舌象拍照识别"。

### 3.1 舌诊拍照流程(前端)

1. 复用 `ImageUploader.vue` 的 getUserMedia 逻辑,新增**拍摄引导页**:统一姿势(自然伸舌、不卷舌)、距离(15-20cm)、取景框提示舌尖/中/根/边分区;
2. **颜色校准卡**:屏幕显示/打印一张含标准色块(红/黄/白/灰)的卡片,拍舌前先拍卡,后端用色块校正白平衡(色彩一致性是舌诊识别最大的坑,不做校准则舌色全不可信);
3. 连拍 3 张 → 选最佳(清晰度/遮挡自动打分)→ 压缩为 JPEG(base64 ≤2MB);
4. 调用现有 `/api/v1/dx/...` 视觉链路(新增 `POST /api/v1/dx/tongue` 或并入 analyze 的 `tongue_image` 字段)。

### 3.2 舌象特征提取(后端,双保险)

- **主通道 Qwen-VL**:`ai_gateway.vision(image_b64, prompt, provider="qwen")`,prompt 要求返回严格 JSON:
  ```json
  {"tongue_color":"淡红|红|绛|紫|暗|淡白","coating_color":"薄白|白腻|黄腻|黄燥|灰黑|无苔",
   "coating_texture":"薄|厚|腻|燥|滑|剥","shape":"胖大|瘦薄|齿痕|裂纹|点刺","state":"歪斜|颤动|短缩|正常",
   "zones":{"tip":"","center":"","root":"","sides":""},"confidence":0.8}
  ```
- **兜底规则库**:`tongue_rules.json`(按 zone + 主色 + 苔质组合 → 标签),Qwen 不可用或置信度 <0.6 时启用——与现有"AI 静默降级"模式一致。
- 输出标签示例:`舌淡红`、`苔薄白`、`齿痕舌`、`舌尖红` → 并入 `user_labels`,引擎中已有的脏腑/六经规则(舌尖红=心火、齿痕=脾虚等)自动生效,**辨证核心零改动**。

### 3.3 语音问诊

- 首选浏览器 `Web Speech API`(Chrome/Edge 内置中文识别,零成本、零上传);识别文本经"口语词库解析"(`extract_symptom_terms`)转标签;不达标的设备降级为打字。
- 远期(量大时):服务端 Whisper(自建 GPU/API),不影响当前上线。

### 3.4 验收标准

- 标准光照下舌色/苔色识别与医师标注一致率 ≥80%(自建 200 张评测集);
- 拍摄到舌象标签入引擎 <5s(视觉网关 <3s + 引擎 <1s);
- 失败兜底:照片识别失败时回退人工点选,不阻塞问诊流。

### 3.5 成本与工期

- 成本:0 元(设备)+ 视觉 API 调用费(约 3 毫厘/次,与现有网关计价一致);
- 工期:约 2 周(拍摄引导 3 天 + 视觉链路与标签规则 4 天 + 评测集与回归 3 天 + 上线)。

## 四、方案 B:脉诊仪(Web 蓝牙 SDK)+ PPG 手环数据

**目标**:把"切(脉)"客观化,脉象标签从"人点"变"机测",自动触发脉证相参与时间辨证。

### 4.1 脉诊仪直连(前端 Web Bluetooth)

- 选型:已有网页可用的 SDK 类设备,如 [@qihuangai/pulse-device](https://www.npmjs.com/package/@qihuangai/pulse-device)(含 [pulse-wave 插件](https://www.npmjs.com/package/@qihuangai/plugin-pulse-wave)),BOM 千元级;备选任意支持标准 BLE 波形回传的压力/PPG 脉诊仪。
- 兼容性:`navigator.bluetooth` 仅 Chrome/Edge/部分 Android → 检测不支持时显示"请换 Chrome/Edge 或用手动点选",绝不断主流程。
- 前端新增 `PulseDevice.vue`:扫描 → 配对 → 持续采集 30-60s 波形 → 波形实时渲染(Chart/Canvas)→ 完成后组装 `{sample_rate, timestamps[], amplitude[], device_model, battery}` 上报。

### 4.2 波形 → 脉象标签(后端特征提取)

`POST /api/v1/device/pulse` → 特征提取服务(纯 Python/NumPy,无重依赖):

| 波形参数 | 计算 | 映射标签(规则库 `pulse_rules.json`) |
|---|---|---|
| 平均脉率 | 峰间距均值 | >90/分→`脉数`;<60/分→`脉迟`;60-90→`脉缓` |
| 节律 | RR 间期变异系数 | 变异>阈值→`脉结代`(提示进一步心电图) |
| 波形力度 | 主波幅/降支比 | 幅高实大→`脉实`/`洪`;幅低→`脉虚`/`细` |
| 波形浮沉 | 轻压/重压两档幅值比 | 轻取明显→`脉浮`;重取明显→`脉沉` |
| 滑涩 | 重搏波/切迹特征 | 需设备 ≥200Hz 采样;PPG 级设备仅输出"脉率/节律/强弱",不强行给滑涩(**宁缺毋滥,标注"该设备不支持"**) |

- 单点压力/PPG 设备**只给**脉率、节律、强弱三类标签(客观可达);浮沉滑涩需 ≥3 点压力阵列设备(见方案 C)——这是中医客观化的诚实边界,写进文档与 UI 提示。
- 标签产出后:`脉微细` 等词自动触发已有 `_discern` 真寒假热/真热假寒鉴别;脉象标签并 `user_labels` 参与八纲虚实、六经、脏腑打分。

### 4.3 PPG 手环/手表(健康云导入)

- 数据来源:华为运动健康/Apple HealthKit 导出(心率、静息心率、睡眠分段、HRV);
- 上传方式:`POST /api/v1/device/ppg_import`(JSON 导入,格式校验 + 大小限制),前端"导入健康数据"页;
- 应用:①实测**夜间加重/五更觉醒** → 自动带出 `time_key`(night/dawn)进 `_time_dx`;②长期静息心率趋势 → 疗效自评的一个客观维度;③与五运六气卡并排显示"今岁气候 ↔ 本人节律"对照。

### 4.4 验收标准

- 脉率/节律标签与人工触诊一致率 ≥95%(节律类);
- 蓝牙连接成功率 ≥90%(Chrome/Edge 桌面 + Android),失败可完整降级;
- 脉象波形上传 → 标签入引擎 <3s;
- 评测集:自采 100 例波形 → 医师标注脉象 → 回归测试(不碰辨证规则库)。

### 4.5 成本与工期

- 硬件:脉诊仪 1 台(约 500-2,000 元,按 SDK 官方型号购买);手环零采购(用户自带);
- 工期:约 3-4 周(蓝牙前端 5 天 + 特征提取与规则 5 天 + 健康数据导入 3 天 + 评测回归 5 天)。

## 五、方案 C:医院级四诊仪网关(舌面脉一体)

**目标**:接入主流医院在用设备(如[道生舌面脉信息采集体质辨识系统(四诊仪)](http://m.whptkd.com/pd.jsp?pid=176)一类,招标价数十万级),面向合作医院/诊所落地。

### 5.1 部署形态(设备网关模式)

```
医院内网:四诊仪工作站 ──(厂商局域网接口/串口/数据库导出)──► 网关小主机
网关小主机(Linux 2U/NUC):驱动适配 + 数据清洗 + 院内网加密上传
                              │ HTTPS(双向校验 + 设备证书)
                              ▼
                   杏林汇 /api/v1/device/simo (四诊仪JSON)
```

- 厂商接口各不相同 → 网关内按"适配器"插件化:每个型号一个 adapter(串口解析/网络 SDK/数据库轮询),输出统一 `simo_json`(舌/面/脉/体质四段),**平台只认统一契约,不绑厂商**;
- 医院内网不通外网时:网关支持离线缓存 + 定时批量上传(断点续传),或医院自建杏林汇内网版(后端容器化,同一套镜像)。

### 5.2 统一数据契约(示例)

```json
{
  "device_id": "hash...", "model": "DS01-A", "firmware": "3.2.1",
  "collected_at": "2026-08-31T10:00:00+08:00",
  "tongue": {"image_url": "…", "color": "淡红", "coating": "薄白", "zones": {"tip": "红", "root": "腻"}},
  "face": {"color": "面赤", "luster": "少泽", "confidence": 0.82},
  "pulse": {"positions": {"cun": [..波形..], "guan": [..], "chi": [..]},
            "labels": ["脉浮", "脉数"], "params": {"rate": 92, "tension": 0.7}},
  "constitution": {"type": "气虚质", "score": 76}
}
```

### 5.3 与辨证引擎的对接

- `tongue/face/pulse` 段 → 标签 → `user_labels`(与 A/B 完全相同);
- `constitution` 体质辨识 → 与**五运六气出生年禀赋**(`_wuyun.birth`)互参:卡上并排显示"设备测体质:气虚质 ↔ 禀赋:金运太过偏燥",冲突时给出取舍提示;
- 三部九候脉(寸关尺三路波形)可升级 `_discern` 与脏腑定位规则(左寸候心、右关候脾等)——**这是 C 档相对 B 档的中医深度增量**。

### 5.4 验收标准与合规

- 统一契约适配至少 1 个真实型号并通过医院内网联调;
- 合规要点:设备属二类医疗器械,杏林汇只做"采集+辅助分析",**不替代器械本身的诊断结论**;报告显著位置声明;院内数据不出院时走内网版部署;涉及真实患者时按等保 2.0 与告知同意办理(平台已有匿名架构,内网版需补实名与权限体系,单独立项)。

### 5.5 成本与工期

- 硬件:四诊仪 1 台(约 20-50 万元,招标采购;合作医院可先借机联调)+ 网关小主机(约 2,000 元);
- 工期:约 6-10 周(适配器框架 2 周 + 首型号适配与联调 3 周 + 体质互参与回归 2 周),内网版部署另计。

## 六、三方案对比与决策

| 维度 | A 手机舌诊+语音 | B 脉诊仪+手环 | C 四诊仪网关 |
|---|---|---|---|
| 硬件成本 | 0 | ~2,000 元 | 20-50 万 |
| 平台开发量 | 小(视觉链路已有) | 中(蓝牙+特征提取) | 大(网关+适配器+内网版) |
| 中医深度增量 | 舌诊客观化 | 脉诊客观化(有限参数) | 舌面脉一体+三部九候+体质互参 |
| 病患获得感 | 高(零门槛) | 中(需 Chrome+设备) | 医院场景专享 |
| 主要风险 | 光照/色彩一致性 | 蓝牙兼容、设备能力边界 | 厂商接口封闭、医疗器械合规 |
| 建议时机 | **立即** | A 完成后 | 有合作医院/诊所时 |

**推荐路线:A → B → C 递进**(每档的"标签入引擎"通路完全复用,不返工)。

## 七、下一步(决策点)

1. 若选 **A**:立项即做,预计 2 周上线,先买/自制一张色彩校准卡并建 200 张舌象评测集;
2. 若选 **B**:先采购 1 台带 SDK 的脉诊仪真机(以官方 SDK 兼容列表为准),真机到手再启动蓝牙联调;
3. 若选 **C**:先找一家合作医院/诊所出借四诊仪联调,再决定网关开发投入。
